## 2. 07-PLAN §6.1 门槛复核

总纲把普通无 Tool 私聊端到端 P50 −35% / P95 −20% 写成硬发布门，同时要求先有冻结的 3.5.3 成对回放。07-PLAN §6.1 指出：若 Planner 只占端到端较小比例，该百分比可能数学不可达，必须先复核而不是假装测过。

| 项 | 记录 |
|---|---|
| 决策点 | R5 发布性能报告时 |
| 证据 | 仓库内没有脱敏 600 轮回放集，也没有同一 Provider/Profile 的 3.5.3 成对 canary |
| 本地结构事实 | 普通文本轮次进入 Main Agent 前的生成式/路由模型调用为 0；3.5.3 对已准入轮次仍有 1 次 Planner 请求 |
| 不可达风险 | 端到端延迟若由 Main Agent 网络时间主导，删除 Planner 不足以保证 −35% / −20% |
| 结论 | **不调整总纲数字，也不用合成延迟去“凑”门槛。** P50/P95 百分比门保持未认证。本地 25 ms Search 与 100 ms 前置增量按下面实测认证 |
| 谁可以改门槛 | 产品负责人根据未来成对回放批准；本报告无权改总纲 |

## 5. R5 §10 必填栏

### 5.1 P50 / P95 端到端延迟

未测。没有成对 3.5.3 / 3.6.0 回放，不填写毫秒。

### 5.2 每轮模型调用

| 口径 | 3.5.3 结构 | 3.6.0 结构 | 回放 |
|---|---|---|---|
| 普通无 Tool 私聊 foreground generative | Planner 1 + Agent 1 | Agent 1 | 未测 |
| 进入 Agent 前的 router/planner | 1 | 0 | 结构 |

Vision、Embedding、后台 Attribution 必须另列；本次本地脚本把它们排除在外。

### 5.3 删除的 Planner 调用

每个原先会跑 Planner 的准入轮次少 1 次生成式路由请求。私聊 / @ / 回复机器人在 3.5.3 仍会跑 Planner；3.6.0 不再评分、不再请求 Planner。低分群聊两边都是本地拒绝，没有 Planner 可删。

### 5.4 Prompt / completion / cached tokens

未测。没有模型调用，不能报 Token。缓存前缀变化（首轮只常驻 `request_tools`）要等成对回放。

### 5.5 首轮 Tool 数量与 schema tokens

结构：首轮常驻 `request_tools`，其余由 authority-first exposure 在 schema budget 内选择，上限 12。本机测量用 20 个 core descriptor 建索引，不展开一次真实 `ChatService` 曝光，因此不报“某次真实轮次的 schema tokens”。

### 5.6 Capability Search 延迟

Core catalog，20 个文档，warm index，200 次，查询见 JSON。

| | P50 (ms) | P95 (ms) | P95 95% CI |
|---|---|---|---|
| Warm search | 0.045 | 0.054 | 0.053–0.055 |
| Cold rebuild（另报，不计入 25 ms） | 0.79 | 0.99 | 0.83–1.00 |

### 5.7 首轮 Tool 命中与 `request_tools` 使用率

未测。没有固定 K、schema budget 和语料版本的标注集。

### 5.8 Memory 纯检索 / prepare / mutation

合成库：3 人 × 4 条 fact、20 条 chat event。只测 `SQLiteMemoryFTSIndex.search`（lexical）。不含 Embedding、Vision、完整 `MemoryTurnSession.prepare`、receipt bookkeeping。

| | P50 (ms) | P95 (ms) | P95 95% CI |
|---|---|---|---|
| Lexical FTS | 1.40 | 1.89 | 1.79–1.96 |
| Mutation | 未测 | 未测 | — |

## 6. 本地 Runtime 前置 100 ms 门

口径：authority/resolver、Capability Search、SQLite/FTS retrieval、budget、exposure/Receipt bookkeeping。不含远程 Vision、Embedding、生成式模型。DB 时间算在本地 Runtime 内。

本次合成循环实际包含：

- `LocalAutonomousParticipationPolicy.evaluate`
- warm `FtsCapabilitySearchIndex.search`
- `SQLiteMemoryFTSIndex.search`

未纳入计时：authority/resolver、schema budget 裁剪、exposure 组装、Recall Receipt 写入。这些是进程内工作，但没有被这次循环覆盖。

| | P50 (ms) | P95 (ms) | P95 95% CI |
|---|---|---|---|
| 已测组合 | 1.68 | 2.17 | 2.05–2.33 |
| Admission only | 0.0075 | 0.014 | 0.010–0.023 |

已测组合 P95 约 2.2 ms，低于 100 ms。缺测的 bookkeeping 若要把总 P95 推过 100 ms，需要再增加约 98 ms；当前代码路径没有对应的远程调用。完整 `handle_turn` 前置仍应在有回放集时重测。

Admission 单测 P95 0.014 ms。群聊低分拒绝停在这一步，不再做 Search 或 Memory。

## 7. 并发与一致性

Memory Prefetch 与 Capability Search 在代码上可以并发，但这次测量是串行的，避免把重叠时间说成“已经证明结构化并发”。生产实现不得为了抢这 100 ms 而放松 SQLite 事务边界。

## 8. 结论

- 本地 Capability Search warm P95 和已测前置组合通过 25 ms / 100 ms 门。
- 普通文本不再有前置 Planner/Router 生成式调用。
- 端到端延迟百分比、Token、Recall@K、`request_tools` 率、mutation 延迟：**没有回放，不认证，不编造。**
- 按 07-PLAN §6.1，百分比门保持原文，等待成对 canary；本报告不是调门槛的批准文件。
