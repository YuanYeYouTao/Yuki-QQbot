# Yuki 主 Agent 聊天历史信封优化讨论稿

## 一、讨论目标

在不修改 `chat_events` 原始存储、不改变 Planner、Memory Worker、Self Reflection、Memory Audit 和 OneBot 发送协议的前提下，只优化主 Agent 收到的聊天历史格式。

目标是：

- 减少群聊中重复发送者、QQ 号和消息编号带来的 token 消耗；
- 在相同历史字符预算内保留更多真实聊天事件；
- 继续准确区分发送者、连续消息、Reply 和 Mention；
- 不重新引入“把别人的话安到当前用户头上”或“把两条消息看成一条”的问题；
- 保持 Yuki 的工具自由度和原生 QQ 回复能力；
- 保持缓存前缀尽量稳定。

## 二、当前问题

当前每条历史消息都会独立渲染完整信封：

```text
[发送者:远野|QQ:2186567848|消息:1874201931] 今晚把记忆写入测试完吧
[发送者:远野|QQ:2186567848|消息:1874201932] 然后再看一下缓存命中率
```

即使两条消息来自同一个人，发送者、QQ 号和长消息 ID 也会重复出现。

线上样本中，15:00 至 15:19 的历史包含：

- 44 条聊天事件；
- 611 个正文字符；
- 3,622 个渲染后字符；
- 其中约 3,011 个字符来自身份和关系信封。

同时，`MAX_CONTEXT_CHARACTERS=12000` 并非全部用于历史正文。人物、群、SELF Memory 等动态元数据会占用相当一部分预算；历史达到高水位后又会按 67% 低水位滚动。因此，重复信封会明显缩短主 Agent 实际能看到的时间跨度。

## 三、范围约束

本次只改变主 Agent 的历史投影。

以下模块保持现状：

- `chat_events` 数据结构和历史数据；
- Planner 的“最近 10 条原始事件 + 当前消息”；
- Planner 当前使用的真实 `reply_to_message_id`；
- OneBot 原生回复发送协议；
- 普通 Memory Worker 和自动记忆提取；
- Yuki Self Reflection；
- User/Self Memory Audit；
- 聊天历史搜索工具返回结构；
- 插件和自动化权限模型。

当前消息仍必须单独传入主 Agent，不能与同发送者的历史合并。

## 四、建议方案：主 Agent 专用消息块

仅在主 Agent 输入中，把连续同发送者的历史事件合并为一个消息块：

```text
[远野#7848|QQ:2186567848]
  [消息:1874201931] 今晚把记忆写入测试完吧
  [消息:1874201932] 然后再看一下缓存命中率

[查无此人#3586|QQ:3135003586]
  [消息:1874201933|回复:远野#7848/消息:1874201931] 你昨天也是这么说的

[Yuki]
  [消息:1874201934] 好，我先检查记忆写入
  [消息:1874201935] 如果失败我会把原因列出来
```

### 身份规则

- 合并依据必须是可信的 `sender_user_id`，不能依据昵称或群名片；
- 模型看到的可读标签使用 `群名片或昵称#QQ尾号`；
- 尾四位冲突时自动扩展到尾六位或完整 QQ；
- Yuki 固定显示为 `Yuki`；
- 每个消息块只展示一次发送者身份；
- 同一发送者离开后重新出现时开启新块；
- `assistant`、`user`、`system` 或外部事件之间绝不跨角色合并；
- 可设置 2 至 5 分钟的最大合并间隔，避免把相隔很久的独立话题误认为同一段表达。

### 消息边界规则

合并只减少重复身份，不能把多条消息正文直接拼成一个段落。每条 QQ 消息必须保留独立行和消息标识，使模型仍能判断：

- 用户连续发送了几条消息；
- Yuki 连续发送了几条消息；
- Reply 指向其中哪一条；
- Mention 属于哪一条具体消息。

Reply 和 Mention 必须放在对应消息正文之前，不能提升到整个发送者块上。

## 五、为什么第一阶段继续保留真实消息 ID

严格限定“其他模块不动”时，主 Agent 消息块中的每条消息仍保留真实 `platform_message_id`。

这样可以保证：

- Planner 继续使用当前协议决定原生 QQ 回复；
- 主 Agent 仍可把历史消息 ID 交给需要消息定位的 OneBot 工具；
- 不需要新增 `m17 -> platform_message_id` 引用解析器；
- 不需要修改工具参数和权限验证；
- 不会出现模型把 `m17` 当作真实 QQ 消息号传给工具的情况。

预计这一阶段可减少约 20% 至 35% 的历史信封开销，收益低于短引用方案，但改动范围和回归风险更小。

## 六、暂不采用的短消息引用方案

更激进的格式是：

```text
[远野#7848|QQ:2186567848]
  m17> 今晚把记忆写入测试完吧
  m18> 然后再看一下缓存命中率
```

它可以进一步减少长消息 ID，但只有配合后端引用解析器才是完整设计：

```text
m17 -> 1874201931
```

否则主 Agent 可能把 `m17` 直接传给 OneBot 工具并导致失败。若未来采用，需要同步设计：

- 本轮引用映射；
- `reply_to_ref` 到 `reply_to_message_id` 的确定性解析；
- 工具参数中的引用解析；
- 对伪造、过期和不可见引用的拒绝；
- 窗口滚动时的引用重建；
- 引用编号的缓存稳定性。

因此短引用不属于本次严格隔离改造。

## 七、实现边界

不应在 PromptComposer 最后一步对已经裁剪好的历史做字符串压缩。那样虽然会减少最终输入 token，但不会补回已经被旧信封预算淘汰的更早消息。

正确顺序应为：

```text
原始 EventRecord
    -> 主 Agent 专用消息块投影
    -> 按紧凑格式计算字符数
    -> 执行历史高低水位裁剪
    -> PromptComposer
    -> 主 Agent
```

建议保留现有单事件渲染接口，并新增仅供主 Agent 使用的批量投影：

```text
ChatEventPromptRenderer
├── render_event(event)          # Planner、自省、审计继续使用
└── render_main_blocks(events)   # 仅主 Agent 使用
```

新方法应复用现有的：

- `event_content()` 正文清理；
- 群名片和昵称选择；
- Reply 目标解析；
- Mention 解析；
- 外部事件不可信标记。

不能重新实现第二套人物归属规则。

## 八、上下文窗口与缓存

消息块压缩后，历史预算应按“块渲染后的字符数”计算。指标需要同时区分：

```text
history_event_count
history_block_count
history_characters
history_anchor_event_id
history_window_rolled
```

窗口锚点仍应绑定真实事件 ID，而不是昵称或块序号。

部署新格式时，主 Agent 的旧 Prompt 缓存会一次性失效，这是预期行为。此后必须保证：

- 已进入窗口的旧消息块不会被每轮重新排序；
- 新消息只追加在历史末尾；
- 当前消息始终单独追加；
- 只有窗口真正滚动时才重建新的历史前缀。

## 九、主要风险

### 1. 消息数量判断错误

如果合并后不保留逐条边界，模型可能把三条消息认为一条带换行的消息。因此每条消息必须保留独立行。

### 2. 同名用户混淆

不能只展示昵称。可读标签必须包含足以消歧的 QQ 尾号，后端身份仍以完整 `sender_user_id` 为准。

### 3. Reply 或 Mention 被错误提升

Reply 和 Mention 是单条事件属性，不能作为整个发送者块的属性。

### 4. 角色边界改变

只能合并相同发送者和相同 provider role 的连续事件，不能跨越 Yuki、人类用户、工具或外部系统事件。

### 5. 输出泄漏内部信封

主 Agent 可能复述新的消息块标记。输出清理器若需要适配，只能匹配明确的内部格式，不能使用会误删正常用户文本的宽泛正则。

## 十、验收建议

至少覆盖以下场景：

1. 同一用户连续发送两至四条消息；
2. 两名用户交替发言；
3. 两名用户使用相同群名片；
4. 一条消息 Reply 同一块中的较早消息；
5. 一条消息 Reply 其他发送者；
6. 一条消息同时包含 Reply 和 Mention；
7. Yuki 连续发送多条消息；
8. 当前消息发送者与最后一条历史相同；
9. 外部事件、插件通知和普通聊天相邻；
10. 历史达到高水位并发生窗口滚动；
11. Planner 的最近十条历史和原生回复行为完全不变；
12. Self Reflection、Audit 和自动 Memory Worker 的输入快照完全不变；
13. 主 Agent 仍能判断每个人说了什么以及分别发送了几条；
14. 与旧格式对比 token、缓存命中率和可见历史时间跨度。

## 十一、建议结论

第一阶段只为主 Agent 引入“连续同发送者消息块”：

- 每个块展示一次完整身份；
- 每条消息继续保留真实消息 ID；
- 每条消息保持独立边界；
- Reply 和 Mention 保持逐消息表达；
- 压缩发生在历史预算裁剪之前；
- Planner、自省、审计、Memory 和 OneBot 协议全部不动。

这是一项收益明确、边界可控的优化。待线上验证身份判断、消息数量判断和缓存表现后，再决定是否进一步引入短消息引用和后端引用解析层。
