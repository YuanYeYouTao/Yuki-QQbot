## 8. 当前主要问题

### 8.1 单条混合来源仍然可能保持混合

这是本次最重要的问题。

现在 Dream 已经能在多个来源之间做语义选择，但模型仍容易把一个 `memory_N` 当作不可继续拆分的基本单位。即使这个来源内部存在多个中心事件，它也可能只输出一个 Episode。

### 8.2 相似度聚类只能判断整条记忆

当前 embedding 表示整条 Episode。只要其中一部分与候选簇高度相关，整条混合 Episode 就会被拉入该簇；随后 Dream 必须负责把来源内部无关的部分重新分离。当前模型并不总能完成这一步。

### 8.3 Preview 与正式执行不是同一份决策

Preview 会调用一次模型，但正式 Start 时会再次调用模型，因此预览中出现的 `keep`、拆分数量和正文不保证与正式执行一致。

本次 Cluster `200` 的预览与正式写入就不同：预览选择保留 `memory_4`，正式执行则对它进行了单来源重组。

### 8.4 evidence 数量较大

新 Fact `472` 继承了165条 evidence，Fact `473` 继承了58条 evidence。审计信息完整是优点，但后续需要确认：

- evidence 数量是否需要去重；
- Dream 输入是否始终只加载有界摘录；
- 数据库存储和管理页面是否会因大量重复 evidence 变慢。

## 9. 建议的下一步

最小修改方向仍应放在 Dream 决策层，而不是重写现有记忆架构：

1. 明确要求模型先识别每个来源内部的中心事件，再决定跨来源组合；
2. 强调一个来源可以同时贡献给多个 output，不得把 `memory_N` 当作不可拆分原子；
3. 每个 output 只能回答“发生了哪一件事或形成了哪一个长期主题”；
4. 同一输出中如果同时出现互不依赖的任务、关系事件或时间段，应继续拆分；
5. 对超过一定长度的单来源 Episode，提高生成多个 output 的倾向，但不使用中文关键词正则进行语义判断；
6. 考虑让管理员批准的 Preview 可以作为正式执行决策直接提交，避免再次调用模型后产生不同结果；
7. 修正后继续使用单簇真实测试，合格后再考虑小批量运行，不直接全库执行。
